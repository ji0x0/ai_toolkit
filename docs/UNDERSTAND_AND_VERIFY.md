# 구현·이해·직접 검증 시간표

## 기본 시간 배분

180분 과제의 기본 목표는 T+60분까지 핵심 구현과 대표 검증을 끝내 인계하고, T+60~170분의 110분을 읽기·직접 검증에 쓰는 것이다. 지연 시 T+80분 인계와 90분 이해·검증을 목표로 한다. 제출 절차 10분은 별도이며, AI 금지 후속 서술형의 30분을 이 시간에 포함하지 않는다.

10시에 시작했다면 기본 인계 목표 11:00, 지연 시 목표 11:20, 이해·검증 마무리 12:50, 과제 제출 절차 12:50~13:00이다. 실제 시작과 플랫폼 타이머·오류·공식 마감에 맞춰 조정한다.

## 코드 인계에 포함할 것

1. 필수 요구별 구현·검증 상태. 미완성·미검증을 분명히 표시한다.
2. 실행 명령·실행 시간, 사용자가 볼 대표 입력과 결과, 현재 코드의 변경 상태.
3. probe.md의 페르소나·페인포인트·원인/근거·해결 원리, 연결 기능과 읽을 파일·함수 순서. 선택안과 대안의 판단 이유.
4. devlog.md의 주요 결정·실패/수정·검증 근거 위치와 다음 행동.
5. 서버를 유지할 터미널, 저장 상태, 이미 알려진 오류와 수정 시 영향.

## 기능 하나를 이해하고 검증하는 순환

| 사용자 행동 | AI가 지원할 것 | 기록할 근거 |
| --- | --- | --- |
| 누가 왜 사용하는지 설명 | 페르소나→페인포인트→원인/근거→해결 원리→기능 연결 | 문제/담당자 답변과 probe의 연결, 미확인 가설 |
| 대표 입력의 결과를 먼저 예측 | 입력과 규칙의 위치 안내, 답은 먼저 대신하지 않음 | 사용자의 실제 예상과 이유 |
| 진입점부터 출력까지 코드를 읽기 | 필요한 파일·함수만 순서대로 설명 | 읽은 위치·아직 모르는 부분 |
| 현재 선택과 대안 비교 | 동일한 기능을 만드는 방법, 장단점, 현재 제약과 결론 설명 | probe.md의 해당 기능 결정 |
| 직접 실행·손계산·UI 확인 | 재현 명령과 중요한 경계/실패 사례 제공 | 기대값·실제값·PASS/FAIL/NOT_RUN/HUMAN_CHECK |
| 본인의 말로 설명 | 실제 코드와 어긋나는 부분만 지적 | 확인된 이해 범위와 남은 질문 |

그동안 AI가 새 기능이나 큰 구조 변경을 진행하면 읽는 대상이 바뀐다. 인계 이후에는 설명·검증 지원과 필요한 오류 수정에 집중한다. 수정은 위치·이유·영향을 알리고 새 diff와 회귀 검증을 확인한다.

## 두 문서의 관계

- devlog.md는 사건 이력이다. 실제 결정·실행·실패·수정이 일어난 뒤 기록하고, 사후 정리는 표시한다.
- probe.md는 문제와 현재 구현의 연결이다. 페르소나·페인포인트·원인/근거·해결 원리, 담당자 질의응답·사용자 판단을 기록하고 기능별 구현·직접 의존성·대안·장단점·선택 이유·검증·사용자 확인으로 연결한다. 기술 검증과 실제 업무 효과는 구분한다.
- 코드/선택을 바꿨으면 probe의 현행 설명을 고치고 devlog에 변경 이유와 근거를 남긴다. 원시 로그는 필요한 경로로 연결한다.
- 문서를 생성·설명했다는 사실은 사용자가 이해했다는 증거가 아니다. 사용자 확인은 실제 답변과 직접 실행 범위로만 표시한다.
