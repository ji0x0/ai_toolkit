# 결과물을 본인의 말로 설명

실제 파일과 실행 결과를 읽고 입력→주요 처리→출력 흐름, 핵심 함수/파일, 중요한 선택, 검증 근거, 한계를 연결한다. 의도한 구조와 구현된 구조가 다르면 차이를 밝힌다.

## 사용자가 코드를 읽는 시간

사용자는 첫 60분에 핵심 구현을 인계받고 110분 정도 이해·검증하기를 원한다(지연 시 T+80분 인계·90분). 인계 시 `probe.md`의 기능 목록과 현재 diff를 안내한다. 사용자가 읽는 파일을 알리지 않고 수정하거나 새 기능을 추가하지 않는다. 요청된 설명만 주고 사용자가 직접 예측·읽기·실행·설명할 시간을 둔다.

기능 하나씩 다음을 진행한다.

1. 작은 입력의 결과를 사용자가 먼저 예측한다.
2. 관련 진입점→핵심 함수→출력을 실제 코드에서 추적한다.
3. probe.md의 선택안·대안·장단점·결론을 읽고 현재 제약에서의 의미를 설명한다.
4. 대표 사례와 경계/실패 사례를 직접 실행하거나 수동 계산으로 대조한다.
5. 본인이 선택 이유·검증·한계를 말한다. 답과 코드가 다르면 해당 지점만 다시 확인한다.

probe.md의 사용자 이해 상태는 실제 확인한 범위만 갱신하고, devlog.md에는 질문·직접 실행·확인한 사실과 남은 부분을 짧게 남긴다. AI가 설명문을 만든 것만으로 사용자 이해 완료라고 쓰지 않는다. 필요한 경우 `record-work`의 문서 기준을 읽는다.

설명은 다음 연결을 중심으로 한다.

- 문제와 사용자 결정 → 선택한 범위.
- 비교한 대안 → 현재 선택의 이유와 포기한 점.
- 중요한 규칙 → 구현 위치와 작은 예시.
- 주장하는 결과 → 실제 검증·표본·실행 조건.
- 실패 조건 → 현재 처리와 남은 개선.

연습을 요청받으면 한 번에 한 질문을 하고 답을 기다린다. 사용자 답을 실제 구현과 대조해 사실 오류와 설명 개선점을 짧게 알려준다. 그럴듯한 모범 답안을 외우게 하거나 존재하지 않는 결정·실험을 지어내지 않는다.

대표 질문은 “이 입력은 어디서 어떻게 처리되나?”, “왜 이 대안을 택했나?”, “어떤 결과가 맞음을 확인했나?”, “조건이 바뀌면 어디가 실패하나?”다. 실제 후속 시험 문항을 예측했다고 주장하지 않는다.

현재 단계에서 AI 사용이 금지되어 있다면 설명·답안 생성·검토를 수행하지 않는다. 이 스킬과 사전 생성 설명은 금지된 단계에 답안을 반입하거나 AI 사용을 지속할 권한이 아니다.
