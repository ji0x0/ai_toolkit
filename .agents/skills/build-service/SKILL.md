# 작동하는 서비스 구현

## 구현 전

- 상세 구현 브리핑과 사용자 확인이 현재 범위에 대해 완료됐는지 확인한다. 직접 호출됐더라도 확인되지 않은 새 과제는 답변 반영·예상 화면/사용 흐름·기능별 입출력/예외·범위·데이터/구조·기술/대안·위험/검증·시간을 채팅에 자세히 설명하고 사용자 확인을 기다린다. 확인 전에는 업무 코드·뼈대 복사를 시작하지 않는다. 이미 합의한 범위의 통상 구현·오류 수정은 반복 확인하지 않는다. solve-task가 사용 가능하면 그 스킬의 `references/implementation-brief.md`를 상세 기준으로 읽고, 선택 설치로 없더라도 이 확인 절차는 유지한다.
- 실제 실행 명령·의존성·기존 구조·데이터 계약을 확인한다. 이미 작동하는 스택을 보존한다.
- 새 구현·수정을 시작하기 전 예상 소요 범위(구현·검증·기록 포함), 근거/미확인 조건, 현재 인계 목표에 주는 영향을 짧게 알린다. 첫 실행이나 오류·범위 변경으로 추정이 달라지면 남은 시간을 갱신한다. 시간 안내 때문에 이미 승인된 통상 작업의 시작 승인을 다시 요구하지 않는다.
- 새 앱의 실행형 코드가 필요하면 [뼈대 선택](references/starter-selection.md)을 읽는다. React·FastAPI·SQLite·RAG·CSV/ML·Docker 모듈을 필요한 조합으로 사용하고, 기본 예시를 실제 요구로 바꾼다.
- 개발 서버가 아니라 결과물을 받는 사람의 사용 조건으로 형태를 결정한다. 설치·서버 실행이 불가능한 사용자에게 서버형 앱을 임의로 전달하지 않는다. 저장·협업 요구와 사용 조건이 충돌하면 담당자에게 확인하고, 가능한 형태를 probe.md의 선택안/대안으로 비교한다.
- 사용자 핵심 동작 하나를 입력→처리→출력/저장으로 추적한다. 필수 화면과 선택 화면을 구분한다.
- 합의한 담당자 질의·답변 단계가 있으면 그 답변과 사용자 결정을 반영한 뒤 구현한다. probe의 페르소나→페인포인트→원인/근거→해결 원리와 기능을 연결하고, 중요한 업무 정책이 미확인이면 해당 로직은 사용자 판단 전 확정하지 않는다.
- 계산·판정·집계는 확인 가능한 함수로 분리한다. 데이터나 숫자를 시연용 상수로 바꾸지 않는다.

## 구현 순서

1. 실행 가능한 최소 경로를 만든 뒤 바로 실행한다. 화면과 API를 따로 완성한 뒤 마지막에 연결하지 않는다.
2. 요청/응답 계약을 명확히 하고 정상·빈 결과·잘못된 입력·서버 오류 상태를 구현한다. 로딩 표시가 필요한 동작에는 완료/실패 상태를 둔다.
3. 요구된 저장이 실제 재조회·새로고침 후에도 유지되는지 확인한다. 데모 데이터는 합성이라고 표시하고 실제 데이터와 구분한다.
4. 좁은 화면·긴 텍스트·빈 목록·중복 클릭을 점검한다. 폼에는 라벨, 결과에는 단위·기간·분모를 표시한다. 버튼을 실제 결과와 연결한다.
5. 사용자 입력을 명령·HTML·SQL로 그대로 실행하지 않는다. 인증·권한이 필요한 과제면 서버에서도 권한을 검사하고 키는 클라이언트에 넣지 않는다.
6. 핵심 경로와 중요한 실패에 대해 기존 테스트 도구로 검증한다. UI의 육안·클릭 확인은 사용자가 플랫폼 내 Browser에서 직접 수행할 절차를 적는다.

서비스 구현을 시작하면 별도 요청 없이 [SERVICE.md 작성 기준과 양식](references/service-document.md)을 사용해 실제 과제 폴더의 서비스 기술 설명서를 생성·갱신한다. 과제 README.md/readme.md는 보존한다. 현재 컴포넌트 관계·Mermaid 아키텍처/대표 흐름·API 명세·업무/운영 규칙과 근거·검증·효과/한계를 설명하고 probe.md·devlog.md에 연결한다. 계획 확인 전에는 업무 구현을 시작하지 않으며 문서도 현재 구현과 계획을 구분한다.

서버/API가 있는 웹서비스에는 [상태 확인·API 안내·접속 정보](references/service-access.md)를 적용한다. 기존 상태 경로·인증·문서 공개 정책은 유지하고 실제 포트/경로와 검증 결과를 SERVICE.md에 기록한다. 프런트 전용 결과물에는 API 해당 없음과 실제 연결을 설명하고 안내용 API 서버를 새로 도입하지 않는다.

사용자의 기본 목표는 T+60분 핵심 구현 인계다(지연 시 T+80분 목표). 완주와 필수 검증을 먼저 확보하고 이후 기능 확장을 멈춰 사용자의 코드 이해·검증 시간을 남긴다. 기능이 생기거나 기술 선택이 달라지면 `record-work`에 따라 devlog.md에 실제 변경을, probe.md에 기능별 도구·대안의 장단점·선택 이유·검증 근거를 갱신한다.

## 제공 웹 IDE에서 실행

- 실행 중인 서버의 실제 포트를 확인하고 `0.0.0.0`에 바인딩한다. 해당 터미널은 유지한다.
- 내장 Browser의 포트·경로를 맞춰 확인한다. 임의 터널·외부 배포·다른 접속 경로로 제한을 우회하지 않는다.
- 브라우저 자동 조작·Computer Use를 실행하지 않는다. HTTP·단위·통합 검증과 수동 UI 확인을 구분한다.
- 연결 실패는 서버 로그→프로세스 유지→포트→바인딩→경로 순서로 좁힌다. 무관한 재설치를 반복하지 않는다.

React 등이 실제 스택일 때만 관련 최적화 자료를 검토한다. 필수 기능이 작동하기 전에 새로운 프레임워크·디자인 시스템·인증·외부 API를 추가하지 않는다.

반환: 실행 명령, 화면·상태·API 안내의 실제 포트/경로, 구현한 사용자 흐름, 실제 검증 근거, 수동 확인할 동작, 남은 한계.
