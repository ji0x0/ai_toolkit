# SERVICE.md 작성

서비스 구현 시 실제 업무 폴더의 SERVICE.md를 준비한다. 업무 설명 README와 기존 사용자 문서는 보존한다. 경로 충돌은 덮어쓰지 않으며 추가 문서가 제한되면 허용된 위치를 확인한다.

[양식](../assets/SERVICE.template.md)은 관련 구획만 사용한다. SERVICE는 현재 구조/계약/운영/검사 상세, probe는 문제·선택/대안·핵심 결과, devlog는 실제 사건을 맡는다. 같은 긴 설계를 복제하거나 매 설명 턴에 세 문서를 다시 쓰지 않는다.

## 필요한 내용

- 목적/범위와 실제 사용자 목표별 유스케이스: 선행 조건·정상 단계·대체/실패·완료 조건.
- 실제 컴포넌트/모듈 책임·코드 위치·입출력/단위·호출/상태 소유와 데이터 방향. 화면 URL/내부 탭과 HTTP 라우팅을 구분한다.
- 실제 아키텍처와 대표 입력의 시퀀스/중간 데이터. Mermaid와 관계 표/텍스트 흐름을 연결하고 없는 DB/모델/큐를 그리지 않는다.
- API 메서드/경로·목적·입력/타입/제약·성공/주요 오류·권한·실제 함수, 합성 예시와 문서 URL의 공개 범위.
- 업무/운영 규칙: 요구·담당자 답변 근거→구현→검사, 실행/종료·설정·저장·실패/복구·접속·상태 범위.
- 테스트 목적·입력·독립 기대값/근거·실제 결과·판정·버전/환경·케이스/명령과 범위/한계. 다수 사례는 목적별 요약 뒤 같은 문서의 상세 목록으로 연결한다.
- 업무 효과는 기대/기술 검증/실제 측정을 구분한다. 미측정 개선율을 만들지 않으며 미구현/미검증·영향·우선순위·다음 확인을 연결한다.
- 핵심 코드의 한국어 주석·읽는 순서·쉬운 용어표. [코드 이해 기준](code-understanding.md)을 적용한다.
