# 180분 안에서 구현과 사용자 이해·검증을 배분

목표는 문서 분량·작업 횟수를 늘리는 것이 아니라 필수 요구가 작동하고 사용자가 판단과 코드를 설명할 수 있는 상태다. 현재 과제 타이머를 기준으로 경과시간을 확인한다. 아래는 사용자의 시간 선호이며 시험의 공식 배점이나 보장된 구현 시간은 아니다.

## 요청을 받았을 때 예상 시간 안내

- 새 과제 또는 추가 구현·수정 요청에서 관련 파일·실행 환경·현재 상태를 짧게 확인하고 작업 전에 추정치를 알린다. 단순 설명·확인 질문에는 매번 추정치를 붙이지 않는다.
- 전체 예상은 범위로 제시하고 상세 브리핑·계획 수정, 구현, 검증·기록, 필요한 설치/실행을 포함한다. 추정 근거와 미확인 조건을 밝힌다. 담당자 답변 전에는 조건부 추정이며 답변/설계 확인 대기 소요를 알 수 없으면 별도로 미정 표시한다. 실제 대기는 전체 경과시간에 포함한다.
- 지금부터 남은 예상 시간, 실제 확인한 과제 경과시간, 예상 인계 지점을 구분한다. 경과시간을 확인할 수 없으면 임의 T+나 완료 시각을 만들지 않는다. 60분/80분은 선호 목표이며 현재 작업의 추정 완료 시간과 같다고 가정하지 않는다.
- 추가 요청은 기존 필수 범위와 인계 목표에 주는 영향을 알린다. 이해·검증 시간을 줄일 경우 포함/보류 대안과 추천을 제시하고, 중요한 범위 선택은 사용자 판단을 기다린다. 실제 과제 마감이나 사용자가 정한 짧은 연습 시간표가 우선한다.
- 담당자 답변 수신, 범위·의존성 변경, 첫 실제 실행, 오류로 추정이 달라진 시점에 남은 시간을 다시 알린다. 지연 원인·변경 추정·범위 조정을 짧게 설명하고 중요한 변동은 devlog.md 현재 상태와 사건 이력에도 반영한다.

안내 형식 예: **작업 예상 X~Y분(브리핑·수정 A~B분, 구현 C~D분, 검증·기록 E~F분 / 확인 대기는 미정). 조건: 실제 확인한 전제/미확인. 예상 인계: 확인 가능한 경과 기준. 기존 목표 영향: 유지/지연과 대안.** 값은 실제 범위와 확인 근거로 채우며 정확한 완료를 보장하지 않는다. 새 계획은 상세 브리핑과 사용자 확인 뒤 구현하고 이미 같은 범위가 확인된 일상 작업은 이 안내 뒤 진행한다.

## 기본 계획: 구현 60 + 이해·검증 110 + 제출 10분

| 경과 | 할 일 | 실제 완료 기준 |
| --- | --- | --- |
| 0~10분 | 시작 감독 절차·README·제출물·기존 환경 파악 | 필수 요구와 제한, 중요한 열린 질문 |
| 10~20분 | 담당자 질문·답변 반영·상세 브리핑·사용자 계획 확인 | 페르소나·원인/근거·기능/결과물·설계/대안·수용 사례와 합의 범위 |
| 20~50분 | 핵심 기능 연결, 구현과 함께 짧은 검증 | 실제 입력→처리→출력의 작동 |
| 50~60분 | 필수 요구 대조·실행·문서와 코드 정합 확인 | 인계 가능한 핵심 구현, 남은 오류·미검증 표시 |
| 60~80분 | 사용자가 전체 구조·대표 경로 읽기 | 실제 파일·함수 순서로 입력 하나 추적 |
| 80~110분 | 기능별 도구 선택·대안·규칙 이해 | 사용자 결과 예측·본인 설명, 모르는 부분 식별 |
| 110~140분 | 대표·경계·실패 사례 직접 검증 | 기대값과 실제 결과 대조, 요구별 근거 |
| 140~160분 | 발견한 필수 오류 최소 수정, 재확인·이해 보완 | 수정 diff와 영향 확인, 사용자 읽기 범위 갱신 |
| 160~170분 | 필요한 최종 실행·정합성 확인 | 저장 상태·제출물·문서·검증의 일치 |
| 170~180분 | 사용자 제출 미리보기·확정 | 이후 후속 서술형 준비 단계 진입 |

## 지연 시

T+35~40분에 남은 필수 기능과 예상 시간을 대조한다. 선택 기능을 줄이고 설치된 도구로 완주한다. T+80분에 인계하면 T+80~170분의 90분을 이해·검증에 사용할 수 있다. 그보다 늦어지면 90분 확보가 안 된다고 명확히 알린다. 필수조건을 임의로 선택 기능으로 바꾸거나 실패를 숨기지 않는다.

질문과 답변 대기도 실제 경과시간이다. 표의 시각이 됐다는 이유로 답을 추정해 코딩하거나 답변 수신 시 타이머를 다시 시작하지 않는다. 기다리는 동안 독립적인 환경·자료 점검과 기록을 하고, 지연이 인계 목표에 주는 영향을 알린다.

표는 목표 배분이며 상세 브리핑을 충분히 이해할 시간을 보장하는 고정 상한이 아니다. 브리핑·계획 수정·사용자 확인이 길어지면 범위·예상 인계·이해 시간을 다시 알린다. 시간 부족을 이유로 사용자 계획 확인을 생략하지 않는다.

첫 완주의 실제 실행 시간을 devlog.md에 기록한다. 최종 전체 실행은 그 소요시간과 여유를 빼서 T+170분 전에 끝나도록 시작한다. 160~170분 표는 긴 실행을 160분까지 기다리라는 뜻이 아니다. 제한 시간 안에 전체 실행이 불가능하면 확인한 대표 범위와 NOT_RUN 범위를 구분한다.

사용자가 읽는 동안 AI는 설명·검증 지원과 합의한 오류 수정에 집중한다. 중요한 수정은 사용자에게 위치와 영향을 알린 뒤 수행하고, 읽었던 버전과 새 버전의 차이를 확인한다. 이해 확인은 실제 답변·직접 실행 범위만 기록한다.

## 시간 경계

이 180분 안의 이해·검증은 과제 수행 단계다. 제출물 확정 뒤에는 파일을 수정할 수 없다. 후속 문항 준비 대기와 6문항·총 30분은 별도이며 모든 단계의 14:00 종료가 적용된다. AI가 금지된 후속 문항에서는 스킬·AI 도움을 중단하고 직접 답한다. 실제 화면과 최신 운영 안내가 우선이다.
