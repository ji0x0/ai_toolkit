# 구현 전 상세 브리핑

문제 분석과 필요한 답변을 반영한 뒤, 사용자가 결과물을 예상할 수 있게 채팅에서 아래 내용을 설명한다. 설명의 길이는 기능과 위험에 맞추되 기술 이름과 작업 목록만으로 끝내지 않는다.

1. **문제와 결과물:** 대상 역할·페인/원인 근거·목표·필수/제외 범위, 실제 사용할 화면/파일 모습과 대표 사용 장면.
2. **기능별 동작:** 입력·주요 처리/규칙·결과·빈 입력/실패/중복 등 예외와 관찰 가능한 수용 사례.
3. **구조:** 유스케이스/사용 흐름, 화면/API 진입점, 단계별 모듈 책임·입출력/단위·저장, 연결 순서와 변경할 위치.
4. **선택:** 실제 기술/구현 방식, 같은 기능의 현실적 대안, 각 장단점·선택 이유·얻고 포기하는 점. 최적화는 강제 조건과 선호 목표·식/우선순위·근거를 설명한다.
5. **실패·환경:** 배경 작업이 있으면 실행 주체·중복/실패/재시작·결과 게시 정책. 접근/화면 전환·권한 등 실제 환경 제약과 충돌 여부.
6. **검증·인계:** 무엇을 어떤 입력/기대값으로 검사하는지, 독립 검사/반례·중요한 조건 변화, 한국어 주석·읽는 지도 준비, 예상 소요·첫 인계·변경 중단·이해 구간.

현재 코드와 계획을 구분하고 불확실한 정책은 확인 대기로 둔다. 필요한 경우 구성/흐름 그림과 작은 입력 예시를 함께 제시한다. 사용자와 기술 선택이 필요한 지점은 추천과 영향을 설명한다.

**새 계획의 구현 전 한 번 확인한다.** 제시한 계획에 대한 실제 진행 의사나 명시 생략 지시를 기록한다. 담당자 답변 전달·침묵·시간 경과는 설계 승인이 아니다. 계획 수정 요청이 있으면 바뀐 부분만 설명하고 확인받는다.

이미 승인된 범위의 통상 구현·검증·오류 수정은 계속한다. 결과물·업무 정책·저장/API 계약·구조·인계 일정이 크게 달라질 때만 변경 부분을 다시 확인한다. 매 단계에 같은 승인 문구를 반복하지 않는다.

probe에 현재 계획/버전·확인 범위와 실제 답변을, devlog에 브리핑/수정/확인 사건을 남긴다. 내부 계획 작성은 설명/승인을 대신하지 않는다. 인계 때 계획→현재 구현→실제 검증 차이를 대조한다.
