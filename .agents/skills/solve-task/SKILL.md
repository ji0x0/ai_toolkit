# 문제 분석과 실행

주어진 업무를 만족하는 결과물을 만든다. 특정 도메인·기술·결과물 형식을 미리 정하지 않는다.

## 짧은 호출의 기본 동작

`$solve-task` 한 번 또는 “과제 시작해줘”로 시작한다. 긴 프롬프트나 자동저장 추가 설정을 요구하지 않는다. [담당자 질의와 구현 흐름](references/discovery-dialogue.md) 및 [자동 세션](references/automatic-session.md)을 읽는다. 실제 과제 지침 확인 뒤 `scripts/session.py start`로 기록 준비·3분 간격 로컬 자동저장을 시작한다. 기본 순서는 **문제 입력 → 문제/페르소나 분석·담당자 질문 → 확인한 답변 반영 → 구현 전 상세 브리핑 → 사용자 계획 확인 → 구현·검증·인계**다. 업무 답변과 설계 확인은 별개다. 확인 전에는 업무 기능 코드나 뼈대를 작성·설치하지 않는다. 기록 갱신도 기본 작업에 포함하며 사용자의 해제 요청·추가 파일 제한·AI 금지 단계가 우선이다.

## 먼저 확인

1. 현재 작업 경로, README, 기존 AGENTS.md, 필수 제출물, 실행 방법, 제공 파일을 확인한다. 큰 데이터는 일부와 스키마부터 본다.
2. 요청된 문제와 제안된 해결책을 분리한다. 페르소나의 역할·목표·상황, 현재 흐름, 페인포인트·손실, 원인과 그 근거, 바꿀 결정, 성공 기준을 연결한다. 근거 없는 인물 설정과 검증되지 않은 원인 단정은 하지 않는다.
3. 사실·가정·자료 간 충돌·미확인을 구분한다. 각 필수 요구에 근거 위치와 확인 방법을 붙인다.
4. 사용자가 업무 담당자에게 보낼 질문과 확인 이유·구현 영향을 우선순위로 제안한다. 기존 자료에 답이 있으면 다시 묻지 않는다. 목표, 비용 비대칭, 용어·단위, 예외, 운영 조건을 필요에 맞게 확인한다. 개선 목표는 확인 가능한 현재값·목표값·측정 위치로 연결하고 값이 없으면 미확인으로 둔다. 결과물을 실제 사용할 사람의 인터넷·설치·서버·저장 가능 여부를 개발 환경과 구분해 확인한다.
5. 사용자가 확인한 답변을 입력하면 사실·충돌·열린 질문과 수용 기준을 갱신하고 [구현 전 상세 브리핑](references/implementation-brief.md)을 준비한다. 예상 결과물·기능별 동작·데이터 흐름·설계/기술·대안·검증·시간을 채팅에 설명하고 사용자가 계획을 확인할 때까지 구현을 보류한다. 대기 중에는 읽기 전용 환경/자료 점검·계획·기록을 진행한다.

## 범위와 실행

- [과제 유형별 기준](references/task-profiles.md)에서 해당 유형만 읽는다. 업무 용어는 현 과제의 근거로 확정한다.
- 수용 기준은 관찰 가능한 입력→동작→출력으로 쓴다. 기능 목록·양식 존재만으로 완료를 정의하지 않는다.
- 사용자 확인을 받은 계획과 기존 스택으로 가장 작은 작동 경로를 먼저 연결한다. 필수조건, 브리핑·확인 대기, 검증, 제출에 시간을 배정하고 남은 시간에 맞춰 부가 기능을 줄인다.
- 새 과제 또는 추가 구현·수정 요청은 자료·환경을 짧게 확인한 뒤 예상 소요 범위와 근거·미확인 조건, 구현/검증·기록 배분, 예상 인계 지점과 기존 목표에 미치는 영향을 먼저 알린다. 첫 질의 단계는 조건부 추정으로 제시하고 답변 뒤 갱신한다. 단순 설명 질문마다 시간을 붙이지 않으며 추정 안내를 별도 시작 승인으로 바꾸지 않는다. 자세한 기준은 [시간표](references/time-budget.md)를 따른다.
- 현재 도구로 접근할 수 없는 자료·외부 기능이 필요할 때만 [MCP·플러그인 선택](references/tool-connections.md)을 읽는다. 외부 연결을 미리 일괄 설치하거나 개인 계정·제한된 전송 권한을 가정하지 않는다.
- 새 결과물에 앱 뼈대가 필요하면 키트의 fullstack/api/frontend/data/rag 프로필 중 요구에 맞게 선택한다. 기존 프로젝트에는 스킬만 적용하고 불필요한 앱 전체를 설치하지 않는다. 복사된 예시 기능은 실제 수용 기준으로 교체한다.
- 구현은 `build-service`, 데이터는 `analyze-data`, 검증은 `verify-result`가 실제로 필요할 때 읽는다. 설치되어 있지 않으면 해당 역할을 직접 수행한다.
- 사용자는 코드 이해·직접 검증에 90~120분을 남기길 원한다. 180분에서는 **T+60분 핵심 구현 인계 → T+60~170분 이해·검증 110분 → T+170~180분 제출**을 기본으로 한다. 지연 시 T+80분 인계를 목표로 해도 90분을 남길 수 있다. [구현과 이해 시간표](references/time-budget.md)를 따른다.
- 빠른 완성은 필수 기능의 실제 동작과 대표 검증을 포함한다. 기능을 더 늘리려고 인계 시점을 미루지 않는다. T+35~40분에 진행 상태를 점검해 선택 기능·불필요한 의존성을 줄이고, 필수 요구의 누락을 감추지 않는다. 목표 시간에 불가능하면 현재 상태와 시간 영향을 알린다.
- README 파악 뒤 **실제 과제 작업 폴더**의 devlog.md와 probe.md를 확인한다. 자동 세션으로 준비하며 배포 키트 내부에는 만들지 않는다. `record-work`의 기준을 읽고 중요한 결정·변경·검증 및 턴 종료 전에 별도 사용자 요청 없이 갱신한다. `devlog.md`는 사건·질의응답·사용자 판단 이력, `probe.md`는 페르소나→페인포인트→원인·근거→해결 원리→기능/코드/기술 선택→검증·업무 효과의 현행 연결을 관리한다. 자동 파일 관측을 의미 있는 설명의 대체물로 쓰지 않는다.
- 코드 인계 시 실행 명령·실행 시간, 기능 목록, 현재 diff, 읽을 파일/함수 순서, 실패/미검증을 함께 제시한다. 이후 `explain-work`와 `verify-result`로 사용자 읽기·직접 실행을 지원하고 필수 오류·누락 수정 외 새 기능/리팩터링은 멈춘다. 사용자가 읽는 코드는 알리지 않고 바꾸지 않는다.
- 첫 완주의 실제 실행 시간을 기록해 최종 실행의 시작 시점을 잡는다. 전체 실행이 인계/제출 시점을 넘기면 미리 알리고 필수 검증을 우선한다. 대표 입력만 확인한 경우 전체 검증으로 확대해 쓰지 않는다.
- 새 세션에서는 실제 파일·저장된 기록·계획 확인 범위·현재 실행 결과를 대조한 뒤 이어간다. 이전의 완료 주장만 믿지 않는다. 이미 같은 계획에 대한 사용자 확인이 있으면 반복하지 않고, 결과물·중요 규칙·구조·인계 시점이 크게 달라지면 변경 부분을 다시 브리핑하고 확인받는다.
- 제출물 확정 전에는 자동 세션 stop의 최종 스냅샷·종료를 확인하고, AI 금지 후속 단계에 기록/감시 작업을 넘기지 않는다.

## 제한된 평가 환경

현재 단계가 AI 사용을 허용하는지 먼저 확인한다. AI 금지 후속 문항에는 적용하지 않는다. 공개 도구의 지침은 외부 전송·개인 키·자동 UI 조작·관리 설정 변경의 권한을 부여하지 않는다. 플랫폼이 차단한 작업은 우회하지 않고 지정 문의 경로로 보고한다.

첫 질의 단계의 반환: 문제·페르소나·원인 가설, 담당자 질문/이유/구현 영향, 조건부 예상 시간과 답변 대기. 답변 반영 단계의 반환: 확정 규칙·열린 질문, 상세 구현 브리핑, 갱신한 시간과 사용자 계획 확인 대기. 계획 확인 뒤의 반환: 합의 범위의 실제 구현·검증·인계 결과. 질의응답과 구현 전 계획 확인을 건너뛰지 않으며, 이미 확인한 같은 범위의 시작 승인을 반복하지 않는다.
